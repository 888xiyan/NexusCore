为了彻底理清这套系统的运作边界，我们首先要在架构上立下一条铁律：“脑手分离（Brain-Hand Separation）”。
 * Bot（大脑/决策体）：运行在内核（Hub）侧，有固定的人格（如“架构师”、“安全审计员”）、长短期记忆，但没有任何直接操作物理机文件或执行 Shell 的能力。
 * Agent Tool（手脚/执行探针）：运行在你的本地电脑、远程 Linux 服务器、Docker 容器或内置浏览器中，只提供算力和工具（如 ast_parse、bash_exec、git_diff），本身没有长期人格，但绑定了特定项目的工作现场（Project Workspace）。
如果不把 “Bot 与 Agent 工具的交流协议” 以及 “Bot 个人记忆 vs. Agent 项目记忆” 拆解清楚，就会出现两个致命问题：① Agent 执行一段 npm build 吐出 5MB 的终端日志，直接把 Bot 的上下文撑爆并污染 MySQL 记忆库；② 你换了一个新的 Coding Bot 来接手项目，它却不知道上一个 Bot 在这个项目里踩过什么坑。
以下是为你设计的 “Bot ↔ Agent 双工通信协议” 与 “双维正交记忆管理模型”：
一、 Bot 与 Agent 工具的直接交流：从“死板 RPC”到“有状态任务流”
传统的 Function Calling 是“一问一答”的同步阻塞模式，但在跨设备、长耗时任务（比如在远程服务器上跑压测、编译代码、爬取多个网页）中完全不够用。内核总线应当采用 基于 JSON-RPC 2.0 扩展的异步流式会话协议（Stateful Task Streaming）。
1. 交互的四阶段握手与接力（以“修复某项目 Bug”为例）
[架构师 Bot] ──(1. 意图调用)──> [内核语义路由 + 上下文水合] ──(2. 注入项目记忆后下发)──> [远程 Linux Agent]
     ▲                                                                                      │
     └──(4. 提炼后的结构化摘要 Artifact)── [内核噪音过滤器] <──(3. 流式日志/请求人类授权)───────┘
 * 阶段一：上下文水合下发（Context Hydration）
   Bot 决定调用远程工具时，只发出轻量指令。内核在转发给远程 Agent 之前，自动从数据库捞出该项目关联的环境变量、代码规范（项目记忆），组装成 TaskContext 信封 一并推给 Agent：
   {
  "jsonrpc": "2.0",
  "id": "task_8848",
  "method": "agent.execute",
  "params": {
    "caller_bot_id": "bot_architect",
    "project_id": "proj_nexus_core",
    "tool": "sandbox_bash",
    "args": { "cmd": "go test -v ./internal/mesh/..." },
    "hydrated_project_rules": [
      "【项目铁律】测试必须开启 -race 竞态检测",
      "【历史踩坑】本地 8080 端口被占用，测试需用随机端口"
    ]
  }
}
 * 阶段二：双向反问与中断（Bidirectional Yield / HITL）
   Agent 工具不是傻瓜式跑完才返回。如果 Agent 探针在执行过程中发现高危操作（如 rm -rf 或修改核心配置），或者发现缺少参数，它可以沿着同一个 WebSocket 管道反向向 Bot（或直接向你的桌面端/手机端）发起 agent.yield_confirm 挂起请求，拿到批准后再继续往下跑。
 * 阶段三：噪音拦截与结果蒸馏（Output Distillation —— 极其关键！）
   远程 Agent 跑完测试，产生了 3000 行堆栈输出。如果直接塞回给 Bot，Token 瞬间爆炸，记忆图谱也会被垃圾填满。
   * 微内核拦截器规则：Agent 回传的数据分为两层——
     * raw_stream_uri：3000 行原始日志直接流式写入内核的廉价冷存储（本地日志文件或 memory_episodes 的 raw_blob 字段），仅推送给前端 UI 的终端窗口供你肉眼查看。
     * distilled_artifact：由 Agent 本地端（利用小模型或正则脚本）提取出的 300 字结构化结论（退出码、报错的具体文件名与行号、核心 Panic 信息），只有这部分精华才会进 Bot 的脑子（上下文窗口）！
二、 核心难题破局：Bot 记忆 vs. Agent 项目记忆的正交管理
为什么一定要把 Bot 记忆 和 项目记忆（Project Memory） 拆开？
想象一个真实场景：
 * 你有一个 “Go 语言专家 Bot”，它同时参与了你的 项目 A（Nexus底座） 和 项目 B（校园网爬虫）。
 * 你还有一个 “安全审计 Bot”，今天被你临时拉进 项目 A 做代码审查。
如果记忆全绑在 Bot 身上，当你把“安全审计 Bot”拉进 项目 A 时，它对 项目 A 的目录结构、架构历史一无所知；反过来，如果“Go 语言专家 Bot”把 项目 A 的专属业务逻辑记在了自己的脑子里，它去写 项目 B 时就会发生严重的跨项目记忆串台（Context Bleeding）！
1. 双维正交记忆矩阵（Orthogonal Memory Matrix）
在微内核的 kernel_entities 表中，我们通过 owner_bot_id（纵向：角色经验） 与 project_id（横向：项目资产） 的交叉组合，将记忆严格切分为四个象限：
| 记忆象限 | 数据库标识 (bot_id × project_id) | 存储内容举例 | 生命周期与归属权 |
|---|---|---|---|
| ① Bot 角色经验记忆
(Bot Persona & Skills) | bot_id = 'bot_go'
project_id = NULL | “主人在写 Go 代码时讨厌用重型 ORM，偏爱原生 SQL 与轻量封装”、“处理并发冲突优先用乐观锁” | 跟 Bot 走：无论这个 Bot 被派去哪个项目、连哪个 Agent，它都带着这套编码品味与通用技能。 |
| ② 项目公共记忆
(Project Knowledge Base) | bot_id = NULL
project_id = 'proj_nexus' | “本项目的核心表是 kernel_entities”、“模块 mesh 负责 WebSocket 路由”、“2026-11-02 决定用 MySQL 9.0” | 跟项目走（团队资产）：沉淀在项目本身。哪怕你把旧 Bot 删了，新建一个 Bot 挂载到该项目，新 Bot 瞬间继承该项目的全部前世今生。 |
| ③ 跨端执行工作现场
(Agent Working State) | bot_id = 'bot_go'
project_id = 'proj_nexus'
scope = 'ephemeral' | “当前正在修改 store.go 第 45 行”、“刚刚在远程服务器 node-ubuntu 上编译失败，报错缺少依赖” | 跟当前任务会话走：任务（Task）一旦合并结项，这段临时草稿记忆就会被压缩成一条【经验教训】，然后原地销毁。 |
| ④ 全局公理库
(Global Vault / Obsidian) | bot_id = NULL
project_id = NULL | 你在 Obsidian 里写的《分布式系统复习笔记》、内置浏览器收藏的通用技术文章 | 跟人类（你）走：最高优先级的只读字典，按需通过向量检索注入。 |
三、 动态装配与自动晋升：两套记忆如何在运行时协同？
有了上面的四象限划分，当你在 VS Code、内置浏览器或聊天软件里向某个 Bot 提问时，微内核的 上下文装配器（Context Assembler） 和 记忆仲裁者（Memory Arbiter） 会像精密齿轮一样咬合运作：
1. 读路径：三层漏斗式上下文注入（Read-Time Funnel）
当你对 架构师 Bot 说：“帮我优化一下当前项目里 WebSocket 断线重连的逻辑。”
内核在调用 LLM 前，会在 50ms 内自动执行一次联合图谱检索，拼装出最精准的 Prompt：
 * 第一层（挂入 Bot 灵魂）：捞取 bot_id = 'bot_architect' 的个人技能记忆（你的通用架构偏好）。
 * 第二层（挂入项目灵魂）：识别出你当前 VS Code 打开的工作区对应 project_id = 'proj_nexus'，捞取该项目下的架构图谱节点、未完成的 PM 看板任务，以及远程 Agent 上报过的该项目目录树摘要（Repo Map）。
 * 第三层（跨端近期感知）：捞取最近 30 分钟内你在内置浏览器或 Obsidian 里打上 #proj_nexus 标签的批注。
> 效果：架构师 Bot 既有它一贯的思考风格，又对当前项目的每一张表、每一个历史 Bug 了如指掌，同时还不会混入其它无关项目的脏数据。
> 
2. 写路径：记忆的“蒸馏与晋升”流水线（Memory Promotion Pipeline）
当 Bot 指挥远程 Agent 工具完成了这次“WebSocket 断线重连”的代码修改并通过了测试，产生的记忆绝对不能一锅粥乱存。内核的 Memory Arbiter 会在后台执行一次记忆分拣（Memory Triage）：
                ┌──> [提炼出：项目新增了指数退避重连机制] ──> 写入【② 项目公共记忆】(project_id = 'proj_nexus')
                │
[任务执行完毕] ──┼──> [提炼出：Go 的 gorilla/websocket 并发写会 panic，需加锁] ──> 晋升写入【① Bot 角色经验记忆】(bot_id = 'bot_go')
                │
                └──> [中间 5 次编译失败的报错日志与临时断点] ──> 标记归档/清理【③ 临时工作现场】
 * 项目特有事实（Project-Specific Fact） \rightarrow 沉入 项目记忆库。同时，如果你的 Obsidian 插件 绑定了该项目的文档目录，Outbox 同步器会自动在该项目的 CHANGELOG.md 或架构笔记里追加一条更新记录。
 * 通用技术认知（Reusable Skill / Pitfall） \rightarrow 晋升到 Bot 个人经验库。下次这个 Go 语言专家 Bot 去给你写另一个开源项目时，它已经天然记住了“写 gorilla/websocket 必须给 Write 操作加互斥锁”这条血泪经验！
四、 数据库与协议层面的落地改造（仅需微调 1 张表 + 1 个协议头）
为了支撑这套强大的“双维记忆管理 + Bot-Agent 交流”，我们在上一版 Schema 的基础上只需做极小的正交扩展：
-- 1. 新增：项目工作区注册表（绑定本地/远程 Agent 的物理目录与项目看板）
CREATE TABLE kernel_projects (
    project_id VARCHAR(64) PRIMARY KEY,
    name VARCHAR(128) NOT NULL,
    repo_uri VARCHAR(512),                -- 关联的 Git 仓库或本地绝对路径
    bound_agent_node VARCHAR(64),         -- 默认挂载在哪台远程设备的 Agent 上执行
    obsidian_folder VARCHAR(255),         -- 映射到 Obsidian 笔记库的哪个子文件夹
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
-- 2. 在通用图谱节点表 kernel_entities 中，实现 (owner_bot_id, project_id) 正交索引
-- 当 owner_bot_id 有值、project_id 为 NULL -> Bot 个人经验
-- 当 owner_bot_id 为 NULL、project_id 有值 -> 项目公共资产
-- 当两者都有值 -> 某 Bot 在某项目下的私有草稿 (Scratchpad)
ALTER TABLE kernel_entities
ADD COLUMN project_id VARCHAR(64) DEFAULT NULL COMMENT '归属的项目空间ID',
ADD INDEX idx_orthogonal_memory (owner_bot_id, project_id, namespace);
五、 全景运转沙盘推演（把你提到的所有模块串起来）
现在，看看你构想的这台“超级机器”在日常开发中是怎么运转的：
 * 起因：你在内置浏览器看了一篇关于《基于时间轮（Timing Wheel）优化百万级心跳检测》的博客，划词批注：@架构师Bot 这个思路不错，记到咱们 Nexus 项目里，把现在的遍历心跳换掉。
 * 记忆入库与分流：
   * 内核收到信封，识别出目标项目是 proj_nexus。
   * 项目管理插件自动在看板生成一个待办卡片：[Task-109] 引入时间轮优化 WebSocket 心跳。
   * Obsidian 笔记插件自动在 Vault/Nexus/架构演进.md 里生成双向链接 [[时间轮心跳方案]]，前端记忆图谱瞬间亮起新节点并连线到 proj_nexus。
 * 跨端协同执行：
   * 你切到 VS Code，在评论框里对 @Go编码Bot 说：把 Task-109 实现了，跑通测试告诉我。
   * 内核把 Go编码Bot 的个人编码偏好 + proj_nexus 的项目记忆（含刚批注的时间轮公式）打包，通过 WebSocket 调度给跑在你 Linux 服务器 Docker 里的 Agent 探针。
   * 远程 Agent 拉起分支、修改代码、跑 go test -race，把精简后的测试通过报告回传给内核。
 * 记忆晋升与通知：
   * 内核通过乐观锁更新 proj_nexus 的架构状态（将旧的“遍历心跳”关系边标为 valid_to = NOW()，激活新的“时间轮心跳”边）。
   * 同时，你在外面用手机打开 Telegram/QQ 聊天 Bot，收到一条推送：“主人，Task-109 已在远程服务器验证通过，Diff 已同步至您的 VS Code 待审阅，项目图谱已更新。”
到这里，微内核拆分、多端插件挂载、MVCC 并发一致性、以及 Bot 与 Agent 的正交记忆管理已经严丝合缝地融合成一套自洽的工业级架构了。
