# NexusCore 整体开发规划（单人）

> 编制时间：2026-11-09（2026-11-12 按 D-22 记忆插件化重排）
> 依据：`NexusCore架构设计总结.md`（Step 0-6 路线）、`内核mvp/内核MVP详细设计.md`（纯内核实现级设计）、`MemoryPlugin/MemoryPlugin详细设计.md`（记忆插件）、`NexusCore待修正问题清单.md`（D-04 / D-11 / D-12）
> 假设：单人全栈（Go 为主 + Python worker + TypeScript 客户端），全职投入，每周交付 demo
> 总体估计：约 90-120 人日（含 25% 缓冲），按里程碑分期交付，任何一期都可独立停线保留

## 1. 单人开发原则

以下原则决定排期顺序，与功能优先级同等重要：

1. **竖切优先**：每个里程碑都以"跑通一条可演示链路"收尾，不做横向铺开。宁可少表少插件，也要先有端到端行为。
2. **CLI 先于 UI**：所有管理动作（建 Bot、授权、DLQ 运营、HITL 确认）先做命令行，Tauri 工作台推到 M7。CLI 就是 MVP 的第一个用户界面。
3. **内核先纯净，插件后复杂**：M1 内核 MVP 不含任何记忆代码与表；`bot-runtime`、`agent-daemon` 是架构强制独立进程，`plugin_memory` 按插件模型（M2 起）独立部署。记忆插件是第一个复杂插件，排在插件生命周期之后。
4. **契约先行的最小集**：proto / schema 先改文件再写代码；两个生成物（protobuf、migrate SQL）进仓库。
5. **测试预算固定**：每个模块 20-30% 的时间给表驱动状态机测试、契约测试与失败注入；不做 UI 自动化，冒烟脚本代替。
6. **改动受验收清单约束**：每个里程碑的完成定义绑定文档里已有的验收问题，不新增临时标准。

## 3. 里程碑详单

### M0 工程准备（3 人日）

1. 仓库目录：`hub/ bot-runtime/ agent-daemon/ cli/ proto/ migrations/ internal/ plugins/`。
2. 自带迁移 CLI `cmd/migrate`（up / down / probe，`_migrations` 记录表），应用 `database/sql + go-sql-driver`，不依赖 golang-migrate 二进制；内核迁移目录 `migrations/kernel`，插件迁移目录 `migrations/plugins/<plugin_id>/{schema...}`（DDL 留待 M1 与 M3 填入）。
3. proto 契约文件 + buf 配置（`buf` 未装时 `make proto` 打印安装提示）。
4. Makefile：`build / build-plugins / test / vet / lint / proto / migrate-probe / migrate-up / migrate-down / smoke-empty / clean`。MySQL 连接通过环境变量 `MYSQL_KERNEL_DSN` 提供（迁移账号与运行账号可分离）；docker-compose 按用户决策推迟到 M2。
5. D-22 落实：`plugin_memory` 目录骨架与插件 manifest 占位；内核二进制不引用任何记忆包。

验收（2026-11-12 重排后）：`go mod tidy + build + vet + test` 全绿（migrate 目录解析含配对冲突用例、Probe 按当前 schema 统计）；`make build` 产出 hub / bot-runtime / agent-daemon / cli / migrate 五个内核二进制，`make build-plugins` 产出 `plugin_memory`（占位）；`bin/hub -version` 打印版本；`cmd/migrate` 缺参正确报错。真库冒烟在配置 DSN 后补跑 `make migrate-probe`。

### M1 内核 MVP（18-24 人日，核心）

按内核 MVP 详设第 3 节的模块顺序实现，每两三天收一次可见行为：

周 1：kernel store + registry + ingress（约 7 人日）

1. `migrations/kernel` 全量 DDL（queue / bot / plugin / ingress / outbox / payload 表）。
2. 凭证签发 / 校验 / 吊销；授权表；订阅登记。
3. `IngressEnvelope` 校验器，失败注入五例：缺因果头 / 路径断裂 / 深度 32 / 根不一致 / 重复幂等键。

周 2：scheduler + outbox + eventbus（约 8 人日）

1. D-04 四语义完整落地：`idempotency_key` UNIQUE、lease 60s + Heartbeat 10s 续租、`suspended` 状态、人工确认幂等 CLI（`resume-list / resume-confirm`，continue / replay / discard 三选一）。
2. `kernel_job_intents` 副作用清单；毒丸 N=5 熔断。
3. Outbox 扫描 → event.deliver job；dedup 幂等；250ms 轮询 + channel 唤醒。

周 3：grpcd + supervisor + bot-runtime + transport（约 6 人日）

1. mTLS 或回环 trust；lease_token 与 AckTask 绑定防双 worker。
2. 懒加载 exec + `binary_digest` 校验 + `idle_ttl` 退出 + 退避重启；`echo_bot` 测试夹具。
3. 反向 TCP + `transport_frame` 校验 + 心跳；loopback agent。

周 4：冒烟与恢复演练（约 2-3 人日）

1. 冒烟八步脚本化；hub 暴露 `/metrics`（队列深度、重试率、DLQ 率、Bot 启动延迟、租约过期率、Outbox 分发延迟）。
2. 演练一次 hub 崩溃恢复（详设 6.5）；账号边界验证（hub 无任何插件 schema 权限）。

退出条件：内核 MVP 详设第 8 节全部通过。**本里程碑不写任何记忆代码、不建任何记忆表。**

### M2 Bot 管理与插件运营（10-12 人日）

1. CLI：`bot create / bot list / bot enable(lazy|resident)`，bot_manifest 入库；`create-bot pull`。
2. 插件生命周期：`plugin install / security-list / security-approve / plugin upgrade / disable / uninstall`；manifest 校验与 `kernel_plugin_event_registry`。
3. 权限：`approve-plugin` 按 3.4 授权，写 `kernel_plugin_grants`；工具授权（`requiring_tools`）。
4. DLQ 运营：查看 / 归档 / 触发 replay（必经人工确认幂等）。
5. MySQL 8 docker-compose 纳入本里程碑（内核运行稳定后再引入）；部署与文档更新都在 M2 收口。
6. Health 最小聚合：`monitor_bot` 心跳超时 / 租约过期聚合报告，发布 `bot.health.changed`。
7. resident Bot 与长连接保活：暂无场景可砍到 M7 之后。

验收：验收问题 1（hub 重启）、3（租约过期）、4（DLQ replay）在真实命令下走通；插件冒烟（PluginMvp §11）通过。

### M3 记忆插件 v1：图谱与笔记（12-16 人日）

1. `plugin_memory` manifest 入库并过 `security_bot` 审查；`memory_bot` 由 `create_bot` 拉起（首个真实插件侧 Bot）。
2. `memory` / `vault` schema DDL（CHECK、可见性索引、账号隔离：图谱账号 / 晋升消费者账号 / 金库账号）；read / search / create 工具。
3. `plugin_obsidian` 首发：`obsidian_note` namespace 注册；单向发布器（DB → .md 幂等渲染）。
4. File Watcher → `IngressEnvelope(source_type=obsidian_file_change)`，带基线 hash。
5. 三方合并 v1 保守化：hash 一致直接摄取；不一致进人工审查队列，不自动合并。
6. 重命名保 entity_id、删除待确认、wikilink 反向边走 `edge_epoch`。
7. 图谱只读视图：先出 HTML 静态页（entities + relations JSON），力导向 UI 留给 M7。
8. 插件事件回投闭环：`memory_outbox` → `memory_bot` 投递委托 → hub ingress。

验收：MemoryPlugin 详设 M3 验收全过；10.3 关键规则三条（重命名 / 删除 / 反向边）各有测试与一个 demo 场景；端起内核仍独立可运行（删除插件验证）。

### M4 认知与晋升闭环（14-18 人日）

1. `plugin_memory` 内 memory-worker 独立进程（Python）；LLM 蒸馏先接本地 Ollama 或回显 stub。
2. Context Assembler：三层装配（Bot 风格 / 项目图谱 / 近期跨端输入），经插件工具返回一次性工件。
3. Memory Arbiter：任务产物分拣（项目事实 / Bot 经验 / 清理）。
4. 晋升链路：晋升队列 → 7.4 版本检查 → `memory_entity_versions` 追加 → Outbox 失效事件。
5. 冲突：乐观锁失败进合并或人工审查（必须有冲突注入测试）。
6. `personal_stack_v1`：Transcripts / Notes / Representations / Injected Context + Auto Dream 整合。
7. D-11 简化：`snapshot_json` 改为 `context_version + involved_entity_ids`；向量侧表保留但停用。

验收：验收问题 5（invalidation 三场景降级语义）+ 7.4 双向冲突各一例；用户级 Bot 记忆隔离用例通过。

### M5 Agent Mesh 实真（10-12 人日）

1. agent-daemon 单机版（Go）：反向 TCP、心跳 15s、工具 Manifest 注册。
2. bash 工具白名单 + 超时与输出截断。
3. 健康上报走 `IngressEnvelope`（继承因果链），进 Health 报告表（`monitor_bot` 聚合）。
4. 流式回传 → `raw_stream_uri` 落文件冷存储；蒸馏 v1 用正则模板（退出码 + 关键错误行）。
5. HITL：`agent.yield_confirm` → job `suspended` + CLI 确认。

验收：验收问题 3 真实场景——长任务执行中 kill Agent 连接，验证第二个 worker 不抢占（suspended 进人工确认）。

### M6 输入通道（10-12 人日）

1. 先做批注浏览器（差异化最大）：Tauri 简壳 + 注入脚本捕获 TextQuoteSelector → `plugin_memory.create(web_clip)`。
2. Telegram 连接器：入口插件转 `IngressEnvelope`，支持 @bot 路由与 fan-out 三副本演示。
3. VS Code 插件推后。

验收：验收问题 2（@三 Bot fan-out 与去重）+ 问题 8（IM 全链路追溯）。

### M7 工作台 UI（10-14 人日）

1. Tauri + React：活动栏 + 主视区。
2. 页面：图谱可视化（`plugin_memory.search` + 关系 JSON）、队列监控（jobs / outbox / DLQ 表格）、replay 人工确认界面、Bot 管理与权限、知识检索。
3. 不做：设置界面、多语言、自动更新。

验收：CLI 全部功能有界面等价物；冒烟链路无终端可走通。

## 4. 分期交付与砍单策略

单人开发必须预设停线点，任何里程碑结束系统都保持可用：

| 停在 | 得到什么 |
| --- | --- |
| M1 后 | 纯内核底座 + 冒烟链路，后续一切的地基（tag v0.1.0-mvp） |
| M2 后 | 可运营的多 Bot / 多插件队列系统（tag v0.2.0） |
| M3 后 | 带知识图谱与笔记的第一版记忆插件（tag v0.2.5） |
| M4 后 | 有记忆闭环的个人知识工作台雏形（tag v0.3.0） |
| M5 后 | 跨设备执行可用（tag v0.4.0） |
| M6 后 | 手机可达的自用产品（tag v0.5.0） |

砍单顺序（从后往前）：M7 UI → M6 的 VS Code → M5 的蒸馏正则精修 → M3 图谱 UI → 保留 M1-M2 与 M4 记忆闭环。任何时刻移除 `plugin_memory`，内核仍可用（M1-M2 能力不受影响）。

## 5. 质量与工程实践

1. **测试结构**：单元（表驱动：状态机 / 校验器）、契约（信封字段、proto 兼容）、集成（docker-compose + 冒烟脚本）、注入（崩溃、超时、双写）。
2. **CI**：单人起步直接用本地 `make ci`（lint + 迁移空跑 + 单测 + 冒烟），成本最低。
3. **分支策略**：主干开发 + 短特性分支；每里程碑打 tag；未完成功能用 env 特性开关，不开长分支。
4. **文档同步义务**：实现与设计偏离时当天回写详设并记修订。
5. **每日节奏**：上午写测试与接口、下午实现、下班前跑冒烟留证据（log 截图入 `doc/evidence/`）。

## 6. 风险与对策

| 风险 | 概率 | 影响 | 对策 |
