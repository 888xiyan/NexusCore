# NexusCore 整体开发规划（单人）

> 编制时间：2026-11-09
> 依据：`NexusCore架构设计总结.md`（Step 0-6 路线）、`内核mvp/内核MVP详细设计.md`（Step 0 实现级设计）、`NexusCore待修正问题清单.md`（D-04 / D-11 / D-12）
> 假设：单人全栈（Go 为主 + Python worker + TypeScript 客户端），全职投入，每周交付 demo
> 总体估计：约 350-450 人日（含 25% 缓冲），按里程碑分期交付，任何一期都可独立停线保留

## 1. 单人开发原则

以下原则决定排期顺序，与功能优先级同等重要：

1. **竖切优先**：每个里程碑都以"跑通一条可演示链路"收尾，不做横向铺开。宁可少表少插件，也要先有端到端行为。
2. **CLI 先于 UI**：所有管理动作（建 Bot、授权、DLQ 运营、HITL 确认）先做命令行，Tauri 工作台推到 M7。CLI 就是 MVP 的第一个用户界面。
3. **单进程非必要不拆**：只有 bot-runtime 是独立二进制（架构要求）；memory-worker 在 M4 前允许库内实现占位，之后才拆进程。
4. **契约先行的最小集**：proto / schema 先改文件再写代码；两个生成物（protobuf、migrate SQL）进仓库。
5. **测试预算固定**：每个模块 20-30% 的时间给表驱动状态机测试、契约测试与失败注入；不做 UI 自动化，冒烟脚本代替。
6. **改动受验收清单约束**：每个里程碑的完成定义绑定文档里已有的验收问题，不新增临时标准。

## 3. 里程碑详单

### M0 工程准备（3 人日）

1. 仓库目录：`hub/ bot-runtime/ memory-worker/ agent-daemon/ cli/ proto/ migrations/ deploy/`。
2. 自带迁移 CLI `cmd/migrate`（up / down / probe，`_migrations` 记录表），应用 `database/sql + go-sql-driver`，不依赖 golang-migrate 二进制；双库差异目录 `migrations/vault`、`migrations/memory`（DDL 留待 M1 第 1 周填入，M0 只建目录与工具）。
3. proto 契约文件 + buf 配置（`buf` 未装时 `make proto` 打印安装提示）。
4. Makefile：`build / test / vet / lint / proto / migrate-probe / migrate-up / migrate-down / smoke-empty / clean`。MySQL 连接通过环境变量 `MYSQL_VAULT_DSN / MYSQL_MEMORY_DSN` 提供；部署方式（本机服务 / docker-compose）按用户决策推迟到 M2。
5. D-12 最小解落实：hub 单二进制 + 双 schema 双凭据（已写入 MVP 详设），记录为完成项。

验收（2026-11-09 已达成）：`go mod tidy + build + vet + test` 全绿（migrate 目录解析含配对冲突用例）；`make build` 产出 hub / bot-runtime / agent-daemon / cli / migrate 五个二进制；`bin/hub -version` 打印 v0.0.1-m；`cmd/migrate` 缺参正确报错。真库冒烟在配置 DSN 后补跑 `make migrate-probe`（docker-compose 属 M2）。

### M1 内核 MVP（22-28 人日，核心）

按内核 MVP 详设第 3 节的模块顺序实现，每两三天收一次可见行为：

周 1：store + registry + ingress（约 7 人日）

1. 双 schema 迁移全量 DDL（含 CHECK 与 `visibility NOT NULL`）。
2. 凭证签发 / 校验 / 吊销；授权表。
3. `IngressEnvelope` 校验器，失败注入五例：缺因果头 / 路径断裂 / 深度 32 / 根不一致 / 重复幂等键。

周 2：scheduler + outbox + eventbus（约 8 人日）

1. D-04 四语义完整落地：`idempotency_key` UNIQUE、lease 60s + Heartbeat 10s 续租、`suspended` 状态、人工确认幂等 CLI（`resume-list / resume-confirm`，continue / replay / discard 三选一）。
2. `kernel_job_intents` 副作用清单；毒丸 N=5 熔断。
3. Outbox 扫描 → event.deliver job；dedup 幂等；250ms 轮询 + channel 唤醒。

周 3：grpcd + supervisor + bot-runtime + transport（约 7 人日）

1. mTLS 或回环 trust；lease_token 与 AckTask 绑定防双 worker。
2. 懒加载 exec + `binary_digest` 校验 + `idle_ttl` 退出 + 退避重启。
3. 反向 TCP + `transport_frame` 校验 + 心跳；loopback agent。

周 4：gateway 最小读写 + 冒烟（约 3-5 人日）

1. read / search（关键词）/ create；条数上限 100。
2. 冒烟八步脚本化；`/metrics` 队列深度、重试率、DLQ 率、Bot 启动延迟。

退出条件：内核 MVP 详设第 8 节全部通过，并演练一次 hub 崩溃恢复（6.5）。

### M2 Bot 管理与队列运营（8-10 人日）

1. CLI：`bot create / bot list / bot enable(lazy|resident)`，bot_manifest 入库。
2. 权限：`approve-plugin` 按 3.4 授权，写 `kernel_plugin_grants`。
3. DLQ 运营：查看 / 归档 / 触发 replay（必经人工确认幂等）。
4. MySQL 8 docker-compose 纳入本里程碑（用户决策：内核运行稳定后再引入）；部署与文档更新都在 M2 收口。
5. Health 最小聚合：心跳超时与租约过期落报告表（聚合评分仍延后）。
6. resident Bot 与长连接保活：暂无场景可砍到 M7 之后。

验收：验收问题 1（hub 重启）、3（租约过期）、4（DLQ replay）在真实命令下走通。

### M3 图谱与笔记（10-14 人日）

1. `obsidian_note` namespace 注册；单向发布器（DB → .md 幂等渲染）。
2. File Watcher → `IngressEnvelope(source_type=obsidian_file_change)`，带基线 hash。
3. 三方合并 v1 保守化：hash 一致直接摄取；不一致进人工审查队列，不自动合并。
4. 重命名保 entity_id、删除待确认、wikilink 反向边走 `edge_epoch`。
5. 图谱只读视图：先出 HTML 静态页（entities + relations JSON），力导向 UI 留给 M7。

验收：10.3 关键规则三条（重命名 / 删除 / 反向边）各有测试与一个 demo 场景。

### M4 认知与晋升闭环（12-16 人日）

1. memory-worker 独立进程（Python）；LLM 蒸馏先接本地 Ollama 或回显 stub。
2. Context Assembler：三层装配（Bot 风格 / 项目图谱 / 近期跨端输入），经 Memory Gateway 只读。
3. Memory Arbiter：任务产物分拣（项目事实 / Bot 经验 / 清理）。
4. 晋升链路：晋升队列 → 7.4 版本检查 → `memory_entity_versions` 追加 → Outbox 失效事件。
5. 冲突：乐观锁失败进合并或人工审查（必须有冲突注入测试）。
6. D-11 简化：`snapshot_json` 改为 `context_version + involved_entity_ids`；向量列保留但停用。

验收：验收问题 5（invalidation 三场景降级语义）+ 7.4 双向冲突各一例。

### M5 Agent Mesh 实真（10-12 人日）

1. agent-daemon 单机版（Go）：反向 TCP、心跳 15s、工具 Manifest 注册。
2. bash 工具白名单 + 超时与输出截断。
3. 健康上报走 `IngressEnvelope`（继承因果链），进 Health 报告表。
4. 流式回传 → `raw_stream_uri` 落文件冷存储；蒸馏 v1 用正则模板（退出码 + 关键错误行）。
5. HITL：`agent.yield_confirm` → job `suspended` + CLI 确认。

验收：验收问题 3 真实场景——长任务执行中 kill Agent 连接，验证第二个 worker 不抢占（suspended 进人工确认）。

### M6 输入通道（10-12 人日）

1. 先做批注浏览器（差异化最大）：Tauri 简壳 + 注入脚本捕获 TextQuoteSelector → `GatewayCreate(web_clip)`。
2. Telegram 连接器：入口插件转 `IngressEnvelope`，支持 @bot 路由与 fan-out 三副本演示。
3. VS Code 插件推后。

验收：验收问题 2（@三 Bot fan-out 与去重）+ 问题 8（IM 全链路追溯）。

### M7 工作台 UI（10-14 人日）

1. Tauri + React：活动栏 + 主视区。
2. 页面：图谱可视化（复用 M3 JSON）、队列监控（jobs / outbox / DLQ 表格）、replay 人工确认界面、Bot 管理与权限、知识检索。
3. 不做：设置界面、多语言、自动更新。

验收：CLI 全部功能有界面等价物；冒烟链路无终端可走通。

## 4. 分期交付与砍单策略

单人开发必须预设停线点，任何里程碑结束系统都保持可用：

| 停在 | 得到什么 |
| --- | --- |
| M1 后 | 内核 MVP + 冒烟链路，后续一切的地基（tag v0.1.0-mvp） |
| M2 后 | 可运营的多 Bot 队列系统（tag v0.2.0） |
| M4 后 | 有记忆闭环的个人知识工作台雏形（tag v0.3.0） |
| M5 后 | 跨设备执行可用（tag v0.4.0） |
| M6 后 | 手机可达的自用产品（tag v0.5.0） |

砍单顺序（从后往前）：M7 UI → M6 的 VS Code → M5 的蒸馏正则精修 → M3 图谱 UI → 保留 M1-M4 与一条输入通道。

## 5. 质量与工程实践

1. **测试结构**：单元（表驱动：状态机 / 校验器）、契约（信封字段、proto 兼容）、集成（docker-compose + 冒烟脚本）、注入（崩溃、超时、双写）。
2. **CI**：单人起步直接用本地 `make ci`（lint + 迁移空跑 + 单测 + 冒烟），成本最低。
3. **分支策略**：主干开发 + 短特性分支；每里程碑打 tag；未完成功能用 env 特性开关，不开长分支。
4. **文档同步义务**：实现与设计偏离时当天回写详设并记修订。
5. **每日节奏**：上午写测试与接口、下午实现、下班前跑冒烟留证据（log 截图入 `doc/evidence/`）。

## 6. 风险与对策

| 风险 | 概率 | 影响 | 对策 |
| --- | --- | --- | --- |
| 人工确认幂等的交互设计拖慢 M1 | 中 | 高 | CLI 先行，路径已定义；UI 延后不阻塞 |
| MySQL SKIP LOCKED 顺序语义实现偏差 | 中 | 高 | 6.6"同分区不越位"用专门测试固化 |
| LLM / 蒸馏质量不可控 | 高 | 中 | M4 用 stub 先打通链路，质量是调参不是架构问题 |
| 双 schema 凭据隔离被开发便利击穿 | 中 | 高 | store 编译期隔离 + lint 禁止 gateway 外引用 vault |
| 三条图形界面线分散精力 | 高 | 中 | 严格按砍单顺序；M7 前不开任何图形界面 |
| 个人精力中断 | 中 | 低 | 停线点设计保证任何阶段可归档 |
